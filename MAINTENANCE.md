# Profile maintenance

Edit `README.md` to update the profile. Keep the hero and about section grounded in established experience and move a technology between stack categories only when the experience supports that change.

## When a showcase changes

1. Update its implementation record, evidence and current status in its own repository first.
2. Update the matching profile project row using the same status: Planned, In Progress, MVP Complete, Tested or Published. Public repository creation alone is not Published workflow status.
3. Adjust the description and stack to the actual implemented scope. Keep planned or optional components explicitly labelled.
4. Add a demo URL only after recording and reviewing a real demonstration with synthetic data.
5. Keep the architecture reference pointing to the current design; label it verified only after comparing it with the running workflow.
6. Recheck the GitHub profile rendering and all repository links.

The full status definitions, artifact checklist and sanitisation instructions live in each showcase's `docs/maintenance.md`:

- [Customer support maintenance](https://github.com/oleafm/ai-customer-support/blob/main/docs/maintenance.md)
- [Lead qualification maintenance](https://github.com/oleafm/ai-lead-qualification/blob/main/docs/maintenance.md)
- [Document processing maintenance](https://github.com/oleafm/intelligent-document-processing/blob/main/docs/maintenance.md)

## Contact placeholders

Replace the website, LinkedIn and email placeholders only with contact details you choose to make public. A connector account email is not automatically a public contact address.

## Evidence rules

Do not add client names, performance claims, testimonials or new certifications without supporting facts. Do not check showcase progress boxes merely because documentation has been written. Review every public change for private information and use a branch and pull request for later updates.
